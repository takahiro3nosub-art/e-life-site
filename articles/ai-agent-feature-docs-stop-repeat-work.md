AIエージェントを使ってバイブコーディングをしていると、こんなことが起きます。

- さっき確認したことを、また聞かれる
- 同じテストが何度も走る
- すでに直したコードを「問題があります」と拾われる
- 古いログやコメントを見て、解決済みの問題が復活する

私が気になったのは、アプリ全体のバージョン管理だけでは足りず、機能や修正した部分ごとに「最新版のメモ」を残したほうがよいのか、という点でした。

先に結論を言うと、**機能ごとに“現在の正しい状態”をまとめたファイルを置く方法は有効**です。

ただし、機能ごとに別々のバージョン管理を始めるわけではありません。

> Gitには「過去に何を変えたか」を残し、機能ドキュメントには「今どう動くのが正しいか」を残す。

この役割分担にすると、AIエージェントが古い情報を現在の問題と勘違いしにくくなります。

## なぜAIは、解決済みの問題を何度も拾うのか

AIエージェントは、毎回すべての経緯を完全に覚えているわけではありません。

新しい作業を始めると、AIはアクセスできる情報や、確認するよう指示された範囲から状況を判断します。そこには、現在のコード、Gitの履歴、コメント、テスト、過去のログなどが含まれます。

このとき、古い情報に「不具合」「未対応」「TODO」と書かれていると、それが現在も残っている問題なのか、すでに解決した記録なのかを見分けにくい場合があります。

また、Gitは変更履歴を見るには便利ですが、「今の仕様だけを短時間で理解する」ための説明書ではありません。

たとえば、ある不具合について5回修正していた場合、Gitには5回分の経緯が残ります。しかし、次のAIが最初に知りたいのは、主に次の3点です。

- 現在はどう動くのが正しいのか
- どの問題が解決済みなのか
- 何がまだ残っているのか

この3点を機能ごとのファイルへまとめておくと、毎回すべての履歴を読み直す必要が減ります。

## Gitと機能メモは、役割が違う

分かりやすく言うと、Gitは日記、機能メモは最新版の説明書です。

| 管理するもの | 主な役割 | 残す内容 |
|---|---|---|
| Git | 過去の変更履歴 | 誰が、いつ、何を変えたか。以前のコードや差分 |
| 機能ドキュメント | 現在の正しい状態 | 今の仕様、処理の流れ、解決済み事項、残っている制約 |
| テスト | 現在の動作の証拠 | 期待する動作が今のコードで通るか |

大切なのは、機能メモを変更のたびに増やさないことです。

`ログイン機能_修正1.md`、`ログイン機能_最新版2.md`、`ログイン機能_本当の最新版.md`のように増やすと、今度はどれが正しいのか分からなくなります。

原則として、1つの機能につき1つのファイルを更新します。過去の内容はGitに残るため、機能メモの中へ古い仕様を全部ため込む必要はありません。

## どの単位でファイルを分ければよい？

細かな修正をすべて別ファイルにすると、管理するメモが増えすぎます。

私は、利用者から見て1つの目的になる機能を目安にするのが分かりやすいと思います。

たとえば、次のような単位です。

```text
docs/features/
├── login.md
├── profile-edit.md
├── payment.md
├── article-publishing.md
└── notification.md
```

ログイン画面のボタン色を変えただけなら、専用ファイルを新しく作る必要はありません。

一方で、ログイン方法、認証API、セッション保存、権限、ログアウト後の動作まで関係するなら、`login.md`へ現在の状態をまとめる価値があります。

目安は、次のどれかに当てはまるかです。

- 複数のファイルや画面にまたがる
- 保存、再読み込み、権限、外部APIが関係する
- 過去に不具合が繰り返された
- 今後も変更される可能性が高い
- 新しいAIが毎回、仕組みを調べ直している

## 作業の流れを固定すると、無駄な確認が減る

機能メモを置くだけでなく、AIエージェントが確認する順番も決めておきます。

### 1. 最初に現在地を確認する

作業開始時は、次の順番で確認します。

1. 対象機能のドキュメント
2. 現在のコード
3. 未コミットの差分
4. 関連する直近のコミット
5. 関連テスト
6. 呼び出し元と利用先
7. 保存、再読み込み、キャッシュ、権限、外部連携

ドキュメントだけを信じるのではなく、現在のコードと一致しているかも確認します。

### 2. 機能を一本道で追う

対象ファイルだけを見ると、直したつもりでも別の画面に反映されていないことがあります。

そこで、可能な範囲で次の流れを追います。

```text
入口 → 入力処理 → 内部処理 → API → 保存 → 表示 → 再読み込み
```

たとえばプロフィール編集なら、「保存ボタンが動いた」で終わりではありません。

入力した内容がAPIへ渡り、データベースへ保存され、画面に表示され、ページを開き直しても残っているところまでが1つの流れです。

### 3. 変更前に、することとしないことを短く示す

AIには、実装前に次を報告させます。

- 現在の動作
- 今回変更する内容
- 今回変更しない内容
- 影響する機能とファイル
- 前提条件
- 起こりそうな失敗
- 実行する確認

ここが決まっていれば、途中で関係のないコードまで直し始めるのを防ぎやすくなります。

### 4. 必要なテストだけを実行する

テストは多ければ多いほどよいわけではありません。

変更した機能の直接テストに加えて、呼び出し元、利用先、保存後、再読み込み後など、実際の影響範囲に合わせて選びます。

空入力、境界値、古いデータ、重複実行、権限違い、API失敗なども、今回の変更と関係があるものだけ確認します。

同じコード、同じ環境、同じ条件ですでに成功している大規模テストを、「念のため」だけで何度も実行する必要はありません。

再実行するなら、少なくとも次のどれかが必要です。

- コードが変わった
- 条件や環境が変わった
- 前回の結果が途中で切れていた
- 新しい失敗経路が見つかった

### 5. 最後に機能メモを更新する

実装と確認が終わったら、同じ変更の中で機能メモも更新します。

ここで残すのは、長い作業日記ではありません。次のAIが読んだときに、現在地がすぐ分かる情報です。

```markdown
# 機能名

## 状態
実装済み / 修正済み / 未対応 / 廃止

## 現在の仕様
現在のコードで有効な動作

## 処理経路
入口 → 処理 → API → 保存 → 表示 → 再読み込み

## 関係ファイル
- ファイルパス

## 解決済み事項
- 症状
- 原因
- 修正内容
- 再発確認方法

## 未対応・既知の制約
- 現在残っている問題だけを記載

## 検証
- 実行したテストと結果
- 実行していない確認

## 最終確認
- 確認日
- 検証時のベースコミットID
- 未コミット差分の有無
```

ここで書くのは、今回の変更自身のコミットIDではありません。検証を始めた時点のベースコミットIDと、その後に未コミットの差分があるかどうかです。

同じコミット自身のIDは、コミットするまで確定しません。IDを書いてからコミットを修正すると、さらに別のIDへ変わってしまいます。今回の変更履歴はGitに任せ、機能メモには「どの状態を基準に、どんな差分を確認したか」を残します。

## 解決済みの問題を、勝手に復活させないルール

機能メモに「解決済み」とあり、その修正が現在のコードにも存在するなら、基本的には再修正しません。

再び対応するのは、次のような証拠がある場合です。

- 現在の環境で問題が再現する
- 関連テストが失敗する
- ドキュメントとコードが明らかに違う
- 新しい変更によって再発する経路がある
- 一部の画面や入口にしか修正が反映されていない

古いログ、昔のコメント、検索で見つけた旧コードだけを根拠に、問題を復活させないことが重要です。

もし再対応するなら、変更前に「再現条件」「今も残っている証拠」「以前の修正では足りない理由」「今回の変更範囲」を示してもらいます。

## ユーザーへの確認も、必要な場面だけに絞る

AIエージェントが何度も確認してくる問題には、確認してよい条件を決める方法が使えます。

確認が必要なのは、主に次の場合です。

- 解釈によって完成形が大きく変わる
- データ削除など、元に戻しにくい操作がある
- 公開、課金、外部送信を行う
- 現在の仕様と依頼が衝突している
- 認証情報や権限が足りない

安全に戻せる小さな実装判断は、合理的な前提を示したうえで進めてもらいます。同じ質問を言い換えて繰り返さないことも、最初のルールへ入れておきます。

## そのままAIへ渡せる短い指示

最初から長い運用ルールを全部入れるのが大変なら、まずは次の指示から始められます。

```text
Gitは変更履歴、docs/features/<feature-name>.mdは現在の正しい仕様として扱ってください。

作業前に、機能ドキュメント、現在のコード、未コミット差分、関連テストを確認してください。
対象ファイルだけで判断せず、入口から保存、表示、再読み込みまで追ってください。

解決済みの問題は、現在の再現、テスト失敗、コードとの矛盾、具体的な再発経路がない限り、再修正しないでください。

同じコードと条件で成功済みのチェックは、理由なく繰り返さないでください。
変更後は、実行した確認、実行していない確認、残るリスクを分けて報告し、機能ドキュメントを最新版へ更新してください。
```

Codexを使っている場合は、プロジェクト全体で守ってほしい基本方針を`AGENTS.md`へ書けます。Codexは作業前に`AGENTS.md`を読み、上位フォルダから作業フォルダまでの指示を組み合わせます。

[OpenAI公式：Custom instructions with AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

ほかのAIエージェントを使う場合は、その製品が指定するルールファイルや設定方法を確認します。個別機能の細かな仕様まで全体ルールへ詰め込まず、`docs/features/`へ分けるのがポイントです。

## 機能メモを作るときの注意点

この方法にも注意点があります。

一番の問題は、コードを変えたのにメモを更新しないことです。古いメモが「最新版」として残ると、かえってAIを迷わせます。

そのため、機能変更の完了条件に「機能メモの更新」を含めます。

また、ドキュメントとコードが矛盾した場合に、どちらかを推測で正しいと決めるのも危険です。その場合は、テストや実際の動作を確認し、矛盾として報告してもらいます。

複数機能にまたがる大きな設計変更は、各機能ファイルだけに分散させず、プロジェクト全体の設計資料やADRと呼ばれる設計判断の記録にも残します。

## まとめ：機能ごとの「最新版」は作る。ただし履歴はGitに任せる

AIエージェントによる重複作業を減らすなら、機能ごとに最新版のメモを残す方法は有効です。

ただし、細かな修正ごとに新しいメモを作るのではありません。

- Gitには過去の変更履歴を残す
- 機能ドキュメントには現在の正しい仕様だけを残す
- 1機能につき原則1ファイルを更新する
- 解決済み問題は、現在の証拠がなければ復活させない
- テストは変更と影響範囲に合わせて選ぶ
- 同じ条件の成功済みチェックを理由なく繰り返さない
- 実装と機能メモを同じ作業で更新する

最終目的は、チェックの回数を増やすことではありません。

次のAIエージェントが、現在の正しい状態を短時間で特定し、必要な範囲だけを変更できる状態を作ることです。
