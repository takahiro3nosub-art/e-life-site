## 先にやることは、謝罪の続きを聞くことではない

AIエージェントから、こんな説明が返ってくることがあります。

> スキルは先に警告していたのに、私が読んで実装するのを怠りました。

このとき、私は「次から気をつけてください」で終わらせないほうがいいと思っています。

確認したいのは、反省の言葉ではなく次の5つです。

1. どのスキルを使ったのか
2. どの指示を見落としたのか
3. どの実装に影響したのか
4. 今回、どこまで直したのか
5. 同じ抜けを何で見つけるのか

ここが分からないまま作業を続けると、別の場所を直したり、必要な確認をもう一度飛ばしたりする可能性があります。

## その発言だけでは、何が起きたのか分からない

「スキルに書いてあった」という説明には、いくつか違う状態が混ざります。

- スキル自体が選ばれていなかった
- スキルは選ばれたが、重要な指示を作業項目へ落とさなかった
- 指示の一部だけ実装した
- 実装はしたが、最後の確認をしなかった
- 作業後にスキルを見直し、見落としへ気づいた

どれなのかで、直し方は変わります。

そのため、「読んだか、読まなかったか」だけを質問しても足りません。

スキル名、該当する指示、変更したファイル、実行した確認を並べてもらうと、現在の状態と照らし合わせられます。

## Codexのスキルは、必要になったときに全文を読む仕組み

ここからは、2026年8月26日にOpenAI公式資料で確認した内容です。

Codexのスキルは、最初からすべての本文を読み込むのではありません。まずスキルの名前と説明を確認し、使うと判断したスキルの`SKILL.md`全文を読みます。これは、必要な情報を段階的に読み込む仕組みです。

スキルを使う方法は2つあります。

- 依頼の中でスキルを明示して呼ぶ
- 依頼内容とスキルの説明が合ったときに、Codexが自動で選ぶ

スキルが多い場合は、最初に見せる一覧から一部が省略され、警告が表示されることも公式資料に書かれています。ただし、スキルが選ばれた後は`SKILL.md`全文を読むと説明されています。

[OpenAI公式：Build skills](https://learn.chatgpt.com/docs/build-skills)

つまり、大事な作業で「自動で選ばれるはず」と任せるより、スキル名を明示し、作業前に関係する必須事項を出してもらうほうが確認しやすくなります。

## まず、見落としの範囲を固定する

すでに実装が進んでいる場合は、すぐ追加修正を始める前に範囲を確認します。

私は、次の順番で出してもらうのが分かりやすいと思います。

| 確認すること | 出してもらう内容 |
|---|---|
| 使用したスキル | スキル名と`SKILL.md`の場所 |
| 見落とした指示 | 要約ではなく、関係する具体的な項目 |
| 影響範囲 | 関係する画面、処理、ファイル |
| 現在の差分 | すでに変更したこと、まだ足りないこと |
| 完了確認 | 実行するテスト、画面確認、再読み込み確認 |

ここで「すべて直します」のような広い返事しか出ない場合は、まだ範囲をつかめていない可能性があります。

特に、保存がある機能なら、ボタンを直しただけで終わらせません。

```text
入口 → 処理 → API → 保存 → 表示 → 再読み込み
```

どこに指示が反映され、どこで確認できるかまでつなげます。

## 作業前に、スキルの指示をチェックリストへ変える

私が試すなら、スキルを読んだという報告だけではなく、今回の作業に関係する部分を短いチェックリストにしてもらいます。

たとえば、画像付きの記事を作るスキルなら、次のようにします。

```text
- [ ] 既存の画像サイズを確認する → public/imagesを調査
- [ ] 本文と画像の内容を一致させる → 記事原稿とaltを照合
- [ ] スマートフォン表示を確認する → 390pxで表示確認
- [ ] 公開後の画像URLを確認する → 本番HTMLと画像URLを取得
```

ポイントは、注意事項だけで終わらず、実装先か確認方法を右側に付けることです。

これなら、最後に同じ一覧をもう一度見て、どこまで終わったかを確かめられます。

## 完了条件を、依頼文の中へ先に入れる

「記事を作って」「この機能を直して」だけでは、AIエージェント側が完了の範囲を決めることになります。

大事な作業では、最初から完了条件も渡します。

```text
完了条件:
- 指定したスキルを使う
- 作業前に関係する必須事項を一覧化する
- 実装後に一覧を1項目ずつ照合する
- 実行した確認と、実行していない確認を分ける
- 公開が必要な場合は、公開URLで反映を確認する
```

「注意してください」よりも、「何を出せば完了か」を決めるほうが、後から判断しやすくなります。

## 絶対に落としたくない条件は、文章だけに任せない

スキルは作業手順を伝えるのに便利です。ただし、毎回必ず守りたい条件を、文章を読むことだけに任せると見落としを完全には防げません。

たとえば、次のような条件は自動確認へ移せる場合があります。

- 必須項目が空ならビルドを失敗させる
- 禁止語が残っていないか検査する
- 指定ページにリンクや画像があるか確認する
- 保存後の値が再読み込みでも残るかテストする
- 公開ページのタイトルやcanonicalを取得して確認する

OpenAI公式資料でも、スキルは1つの仕事へ絞り、命令形の手順と明確な入力・出力を書くことが勧められています。また、決まった動作や外部ツールが必要な場合は、スクリプトを含める構成も案内されています。

毎回守る共通ルール、特定作業の手順、自動で判定できる条件を分けると整理しやすくなります。

| 置き場所 | 向いている内容 |
|---|---|
| `AGENTS.md` | 作業前の確認など、プロジェクトで毎回守る共通ルール |
| スキル | 記事制作、公開確認など、特定の作業手順 |
| テスト・確認用スクリプト | 必須項目、禁止条件、表示結果など、機械的に判定できること |

## 同じ失敗が続くなら、スキルの書き方も見直す

同じ項目が何度も抜ける場合は、AIエージェントだけでなく、スキル側も確認します。

- 1つのスキルに仕事を詰め込みすぎていないか
- 最重要の条件が長い説明の中へ埋もれていないか
- 「確認する」だけで、確認方法や出力が書かれていないか
- 作業開始前と完了前のどちらで読む項目か分かるか
- 実際の依頼文で、そのスキルが選ばれる説明になっているか

公式資料では、スキルを1つの仕事へ絞ること、明確な入力と出力を書くこと、想定する依頼文で正しく選ばれるか試すことが勧められています。

スキルを更新したのに選択肢へ出てこない場合、公式資料ではCodexの再起動が案内されています。

## すでに変な実装をされたときの戻し方

見落としが分かったからといって、すぐ全部やり直す必要はありません。

次の順番で戻します。

1. 追加の変更をいったん止める
2. 見落とした指示と現在の差分を比べる
3. 影響する場所だけを特定する
4. 不足分を直す
5. 最初のチェックリストで再確認する
6. 実行していない確認を残して報告する

すでに別の問題を直している変更まで消すと、被害が広がることがあります。現在の差分を見て、今回の見落としに関係する部分だけを扱います。

過去の問題を何度もやり直す場合は、[解決済みの問題をAIエージェントがまた拾うときの整理方法](/articles/ai-agent-feature-docs-stop-repeat-work/)も分けて考えると、原因を切り分けやすくなります。

## まとめ：反省ではなく、次の確認方法を残す

「スキルは警告していたのに、実装を怠りました」と言われたとき、確認したいのは気持ちではありません。

- どのスキルを使ったか
- どの指示が抜けたか
- どの実装へ影響したか
- 今回どこまで直したか
- 次回は何で見つけるか

この5つを具体的に出してもらいます。

次回からは、重要なスキルを明示して呼び、作業前に必須事項をチェックリストへ変え、完了時に同じ一覧で照合します。

それでも抜ける条件は、テストや確認用スクリプトへ移します。

私はまだ、この方法を長期間使って失敗率を測ったわけではありません。それでも、「次から気をつけます」で終わらず、抜けた場所と確認方法を残すだけでも、次の作業で見るべき場所はかなり明確になります。
